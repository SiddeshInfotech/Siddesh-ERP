SHOWS 33 — barcode/document

product_barcodes.status = INWARDED → v_batch_registry. And inward_items.quantity − Σ outward_items.quantity → v_inward_history.remaining_qty. Neither needs a ledger row.

SHOWS 0 — ledger

Σ stock_ledger.qty_delta → stock_balances → v_current_stock.qty_available. No INWARD rows were ever posted for these 33, so it is 0 — and save_outward holds the lock, so it wins.

Six numbers, three definitions of “how much stock is there,” one of them never decremented. They agree only while the ledger, the barcode statuses, and the document quantities stay perfectly in step — which the ping-pong migrations guaranteed they wouldn’t.

→ The fix, as one consolidated migration

  1. One authoritative definition each of save_inward, scan_receive, save_outward, rebuild_stock_balances, and the stock views — replacing the ping-pong. Pick ledger as the single source of truth; make v_inward_history.remaining read stock-by-batch from the ledger, not document math.
  2. Backfill the stranded units. For every barcode whose status ∈ {INWARDED, AVAILABLE, IN_STOCK} with no matching INWARD ledger row, post one +1 INWARD row — idempotent via uuid_v5(barcode_id) — so the ledger equals physical reality and AVAILABLE reads 33. Append-only rule honoured (no edits, only new rows).
  3. Add received-at / office / scanned-by columns to the Outward batch-allocation table, sourced from v_batch_barcodes.
  4. Then run rebuild_stock_balances() once and assert it’s a no-op — the standing test that cache = ledger.
